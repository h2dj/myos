# 할 일 저장·조회 성능 조사

## 조사 범위

현재 코드의 DB 왕복과 조회 조건을 검토한 결과다. 운영 Supabase/Vercel의 쿼리 실행 시간, 연결 대기, p95 응답 시간은 측정하지 않았다. 따라서 아래 항목은 개선 후보이며 특정 배속이나 운영 병목을 확정하지 않는다. 이번 변경은 모바일 입력 UI에 적용했고 DB 조회·스키마·배포 설정은 유지했다.

## 우선순위

| 순서 | 코드에서 확인한 내용                                                                                                                                                                                                      | 개선 방법                                                                                                                | 검증할 점                                                                                                                                    |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `apps/web/src/app/(app)/tasks/page.tsx`는 프로젝트 선택지의 ID·이름만 쓰지만 `listProjects()`가 전체 프로젝트를 읽고 `attachProgress()`로 할 일 진행률까지 집계한다. 프로젝트가 있으면 불필요한 집계 쿼리 1회가 추가된다. | 권한 검사를 유지하는 프로젝트 선택지 전용 조회를 만들고 할 일 화면에 적용한다.                                           | 프로젝트가 많은 공간에서 쿼리 횟수·읽은 행 수와 화면 응답 시간 비교. 프로젝트 화면의 진행률은 유지.                                          |
| 2    | `packages/domain/src/tasks.ts`의 `attachExtras()`는 태그 조회가 끝난 후 프로젝트 이름을 조회한다. 둘은 서로의 결과를 사용하지 않는다.                                                                                     | 두 조회를 `Promise.all`로 병렬화하거나 필요한 프로젝트 이름을 목록 쿼리에 조인한다.                                      | 독립 커넥션을 사용할 때 대기 구간 감소 여부. 트랜잭션 내부에서는 같은 커넥션이라 병렬 호출만으로 빨라지지 않을 수 있다.                      |
| 3    | 목록의 날짜 필터·정렬은 `coalesce(scheduled_start, due_at)`를 사용한다. 기존 인덱스는 `(workspace_id, scheduled_start)`라 이 표현식 정렬을 그대로 지원하지 않는다. 오늘 이전 완료분 제외 조건도 함께 적용된다.            | 데이터가 커지면 실제 조회의 실행 계획을 보고 삭제되지 않은 항목에 대한 표현식 복합 인덱스와 페이지 단위 조회를 검토한다. | `EXPLAIN (ANALYZE, BUFFERS)`에서 정렬 비용·스캔 행 수 확인. 작은 테이블에서는 순차 스캔이 더 효율적일 수 있어 인덱스를 바로 추가하지 않는다. |
| 4    | 할 일 변경은 `/tasks`, `/dashboard`, `/projects`를 다시 검증한다. 저장 후 화면 갱신 시간에는 재조회·서버 렌더링도 포함된다.                                                                                               | 저장 자체와 재검증 시간을 분리 측정하고, 페이지·태그 단위로 갱신 범위를 좁힐 수 있는지 검토한다.                         | 프로젝트 상세·대시보드·공유 공간의 수치가 즉시 갱신되는지 확인. 범위를 줄여 오래된 화면을 남기지 않는다.                                     |
| 5    | `requireSession()`은 공간 목록과 프로필을 순서대로 읽는다. 운영 인증에서는 Supabase `getUser()` 네트워크 검증도 포함한다. 요청 안에서는 React `cache`로 중복 호출을 합친다.                                               | 기존 사용자 조회를 한 쿼리로 합치거나 첫 가입 초기화와 일반 세션 조회를 구분하는 방안을 검토한다.                        | 신규 가입·공간 전환·탈퇴 및 권한 변경 시 정확성 유지. 권한 조회를 요청 간 전역 캐시로 바꾸거나 인증 검증을 생략하지 않는다.                  |

## 이미 설정된 것과 추가 확인

- 웹의 Vercel 리전은 `apps/web/vercel.json`에서 서울(`icn1`)로 설정되어 있고, 배포 문서는 Supabase도 서울을 권장한다. 실제 운영 프로젝트의 DB 리전과 함수 실행 리전이 일치하는지 확인해야 한다.
- 웹은 Supabase transaction pooler(6543)를 사용하도록 문서화되어 있다. `createDb()`는 해당 포트에서 prepared statement를 끄고 풀 크기를 5로 사용한다. HMR 중에도 풀을 재사용한다. 풀 크기를 무조건 늘리면 서버리스 인스턴스 수에 따라 연결 고갈이 심해질 수 있다.
- `tagsFor()`는 작업별 쿼리가 아닌 ID 묶음 조회다. `attachProgress()`도 프로젝트별 쿼리 대신 그룹 집계를 사용한다. 일반적인 N+1 조회 구조는 아니다.
- `createTask()`의 기본 저장 경로에는 권한 조회, 할 일 INSERT, 감사 로그 INSERT가 있고 트랜잭션 시작·커밋이 필요하다. 프로젝트·태그가 있으면 관련 검증·저장이 더해진다. 감사 로그와 권한 검사를 제거해 속도를 높이지 않는다.

## 운영에서 먼저 측정할 항목

1. 개인 정보·제목·SQL 바인딩 값을 기록하지 않고, 작업 종류별 요청 전체 시간과 인증·DB 연결·쿼리·재검증 구간 시간을 수집한다. 콜드 스타트와 웜 요청, 저장과 목록 조회를 분리해 p50/p95를 비교한다.
2. Supabase의 느린 쿼리/실행 통계에서 할 일 목록·프로젝트 진행률 집계의 호출 횟수와 누적 시간을 확인한다. 필요한 통계 확장·권한은 운영 설정에서 확인한다.
3. 대표 공간의 항목 수와 실제 필터를 사용해 읽기 전용 SELECT의 실행 계획을 확인한다. `EXPLAIN ANALYZE`도 쿼리를 실행하므로 큰 운영 테이블에서는 부하를 고려해 복제본이나 대표 데이터를 가진 검증 DB에서 먼저 실행한다.
4. 우선순위 1부터 하나씩 적용하고 전후 결과를 비교한다. 운영 DB 접근·측정 없이 로컬 DB 시간만으로 운영 개선 효과를 단정하지 않는다.
