# 업무 데이터 내보내기·복원 검증과 성능 측정

2026-10-23 첫 단계 구현. 사용자 기능은 **설정 → 데이터 관리 → 현재 공간 데이터 내보내기**에서 사용할 수 있다. 별도 DB 마이그레이션은 필요하지 않다.

## 내보내기 범위

공간 소유자만 현재 공간의 업무 데이터를 내보낼 수 있다. 서버에서도 `manage` 권한을 검사하며, 반복 가능한 읽기 트랜잭션으로 한 시점의 사본을 만든다. 응답은 `private, no-store`와 첨부 파일 헤더를 사용한다.

- 프로젝트(상위/하위 포함), 활동처, 상시 사업·활동
- 할 일(상태·완료일·일정·활동 연결·반복 회차·휴지통 포함), 반복 시리즈 설정
- 노트, 처리/미처리 인박스, 태그, 항목별 태그, 항목 연결

형식은 `myos-workspace`, 버전 1의 JSON이다. 20MiB/총 100,000행을 넘으면 실패를 알린다. 크기 제한에 걸리거나 전체 DB 복구가 필요하면 별도 PostgreSQL/Supabase 백업을 사용해야 한다. 새 스키마 필드를 추가할 때 백업 버전과 이전 버전 호환성도 검토한다.

이 파일은 **업무 데이터 사본**이다. 로그인/Auth 계정, 이메일·프로필, 공유 멤버·권한, 개인 대시보드, 알림, 자동화 설정·실행 이력, 감사 로그, 서비스 접속 정보는 포함하지 않는다. 따라서 Supabase 전체 백업을 대체하지 않는다. 작성자·담당자 UUID는 업무 데이터의 참조 보존을 위해 포함한다. 파일에는 업무 내용이 들어 있으므로 안전하게 보관한다. SHA-256은 손상 확인용 체크섬이며 암호화나 발신자 인증 서명이 아니다.

## 검증 DB 복원 리허설

준비: Node 22, pnpm 10.28.0, Linux의 로컬 Docker 소켓(`/var/run/docker.sock`), PostgreSQL 16 이미지 접근. 연결 대상 선택 환경변수로 다른 Docker 데몬을 사용하지 않는다. 프록시·인증·인증서 설정은 기존 환경의 것을 유지한다.

```bash
# 내려받은 업무 데이터 사본을 임시 DB에 복원·비교
pnpm --silent backup:verify /안전한/경로/myos-workspace-2026-10-23.json

# 합성 데이터 원본 DB와 복원 DB를 각각 새로 만들어 전체 과정을 검증
pnpm --silent backup:rehearse
```

검증 도구는 새 Docker 컨테이너와 `myos_restore_` 이름의 DB를 직접 만든다. 기존 DB 접속 URL을 인수로 받지 않으며 `DATABASE_URL`을 사용하지 않는다. 연결 포트는 로컬 주소에만 연다. 임시 인증 파일은 0600으로 만들고, 종료 시 자체 컨테이너·볼륨·임시 파일을 정리한다. 강제 종료로 남은 자원은 `myos.backup-verification=1` Docker 라벨로 식별할 수 있다.

복원 함수도 DB 이름과 빈 상태를 재검사한다. 파일 버전·크기·체크섬·중복·다른 공간 데이터·잘못된 참조·프로젝트 순환·반복 회차 중복을 검증한 후 고정된 테이블에만 트랜잭션으로 삽입한다. 원본 항목 ID와 날짜·연결을 보존하며, 부모 프로젝트는 전체 프로젝트 삽입 뒤 연결한다. 작성자·담당자 FK에는 `@restore.invalid`의 검증 전용 가상 프로필을 사용한다. 실제 로그인 계정을 복원하거나 워커·메일을 실행하지 않는다.

복원 뒤 다시 내보내 **공간 정보와 10개 묶음의 개수·내용·연결 체크섬**을 비교한다. 이미 데이터가 있는 검증 DB에 두 번 복원하는 것도 차단한다. 결과에는 개수·체크섬과 검증 결과만 표시한다. 인박스의 과거 변환 결과 ID는 영구 삭제된 항목을 가리킬 수 있어 역사적 값 그대로 보존한다. 이번 단계에는 운영 공간을 덮어쓰는 웹 가져오기 기능이 없다.

`pnpm backup:rehearse`와 `pnpm perf:benchmark`는 CI에서도 실행한다. 성능 검증은 SQL 문장 수 감소를 확인하며 환경에 민감한 지연 시간에는 고정 통과 기준을 두지 않는다. 복원 리허설은 프로젝트 3단계, 활동·활동처, 휴지통, 반복 회차, 노트, 처리/미처리 인박스, 태그와 항목 연결을 포함한 합성 데이터로 검증한다. 실제 운영 데이터의 복원 리허설을 수행했다는 의미는 아니다.

## 성능 변경과 측정

할 일 화면의 프로젝트 선택지는 기존 `listProjects()` 대신 `listProjectOptions()`를 사용한다. 필요한 `id/name/parentId`만 읽으며 접근 권한 검사는 유지한다. 프로젝트 화면의 진행률 집계는 유지한다.

```bash
# 항상 별도의 새 로컬 DB에서 합성 데이터로 비교한다. 운영 DB를 사용하지 않는다.
pnpm --silent perf:benchmark

# 웹 서버에 PERFORMANCE_LOGGING=1을 설정하면 제한된 성능 로그를 기록한다.
# 기본값은 기록하지 않음. 운영 설정 변경 및 재배포는 별도 작업이다.
pnpm --silent perf:report /안전한/경로/performance.jsonl
```

측정 로그에는 고정된 작업 종류·구간·소요 시간·성공 여부만 기록한다. 제목·이메일·사용자/공간/항목 ID·SQL·바인딩 값·예외 메시지는 넣지 않는다. 집계 도구는 알려진 로그만 추출하고 작업/구간별 표본 수·실패 수·p50/p95를 반환한다. Vercel 등의 JSON 로그에서 `message`에 담긴 측정 JSON도 지원한다.

- 작업: 할 일 생성·수정·상태 변경·빠른 작업·삭제·복구, 할 일/프로젝트 선택지 조회
- 구간: 세션 확인, 변경 처리, 캐시 무효화 등록, 액션 전체; 세션 안의 인증 공급자/공간/프로필 조회
- `query`/`mutation` 구간은 권한 검사·연결 대기와 여러 DB 요청을 포함한 서비스 함수 시간이다. 개별 SQL 실행 시간이나 연결 대기만을 따로 측정한 값은 아니다.
- 무효화 등록은 `revalidatePath()` 호출 시간이다. 이후 서버 렌더링과 브라우저 네트워크·화면 반영은 액션 전체 측정 범위 밖이다.
- p50/p95는 최근접 순위 방식이다. 짧은 표본은 참고용이며 운영 판단에는 충분한 요청량과 콜드 스타트/웜 요청, 요청 전체 시간도 함께 확인해야 한다.

## 이번 검증 결과

격리된 로컬 PostgreSQL 16, 합성 프로젝트 103개·초기 할 일 2,005개, 각 작업 워밍업 5회 후 30회 측정. 단위는 ms이며 SQL 수는 ORM 로거가 센 문장 수다(트랜잭션 제어 패킷·네트워크 왕복 전체가 아님).

| 작업                           |   p50 |   p95 | SQL 문장 수 |
| ------------------------------ | ----: | ----: | ----------: |
| 기존 프로젝트 전체/진행률 조회 |  5.05 | 10.69 |           3 |
| 프로젝트 선택지 전용 조회      |  1.84 |  2.30 |           2 |
| 할 일 목록(최대 500개)         | 15.37 | 21.94 |           6 |
| 할 일 저장                     |  3.51 |  6.93 |           3 |

처음에는 테스트·타입 검사·복원 검증을 동시에 실행하면서 측정해 기존/선택지 p95가 23.86/27.04ms였다. 부하 영향을 확인하기 위해 다른 검증 작업이 끝난 뒤 위 단독 측정을 수행했다. 두 실행 모두 프로젝트 SQL 3→2회 감소는 동일했다. 로컬 지연 수치로 운영 서비스가 같은 비율로 빨라졌다고 단정하지 않는다. 운영 p95·콜드 스타트·Supabase 실행 계획은 아직 측정하지 않았다.

복원 검증에서 10개 묶음(활동처·활동·프로젝트·시리즈·할 일·노트·인박스·태그·태그 연결·항목 연결)의 내용과 개수가 일치했다. 일반 DB 복원 거부, 중복 복원 거부, 소유자 이외 내보내기 거부와 손상된 파일 검증도 확인한다.

후속: 운영 측정 로그를 확보한 뒤 `db-performance.md`의 조회 병렬화·날짜 표현식 인덱스·재검증 범위를 실제 병목 순서대로 검토한다. 현재 단계에서는 풀 크기·인덱스·인증 검증 방식은 변경하지 않았다.
